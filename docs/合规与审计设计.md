# 合规与审计设计说明

> 本文说明「账有律」如何在系统层面（而不只是界面提示层面）满足四项监管硬约束。
> 面向：财务负责人、内审、以及需要评估本系统能否用于真实账务的决策者。

---

## 一、四条硬约束，四种结构性保证

| 监管要求 | 系统怎么保证 | 为什么不能靠「提示」 |
| --- | --- | --- |
| 绝不自动向税务局提交 | 代码里不存在任何外发通道；申报状态机里没有 calculated → filed 的边 | 提示可以被忽略；缺少代码路径才是真的做不到 |
| 税务计算必须人工复核 | 草稿 → 已计算 → 已复核 → 已审批，四级状态，每级要人签署，且签名绑定计算指纹 | 只要有一个函数能跳过签署，复核就形同虚设 |
| 禁止物理删除 | 只追加的版本表 + 哈希链事件流；源码级测试禁止 unlink/rm/truncate | 数据库 DELETE 之后再无痕迹，事后无法自证清白 |
| 会计处理必须合法 | 每条结论绑定法条；error 级问题阻断流程，不可豁免 | 「建议性提醒」在真实审计中不构成控制 |

## 二、申报状态机（Human-in-the-loop）

~~~
                    ┌──────────────────────────────────────────┐
                    │                                          │
   ┌────────┐  calculate  ┌────────────┐  review   ┌──────────┐ │  approve  ┌──────────┐
   │ draft  │────────────▶│ calculated │──────────▶│ reviewed │─┘──────────▶│ approved │
   │ 草稿   │             │  已计算    │           │ 已复核   │              │ 已审批   │
   └────────┘             └────────────┘           └──────────┘              └──────────┘
        ▲                        │                                              │
        │       revise           │ reject                                       │ 人工在电子税务局
        └────────────────────────┴──────────────▶ ┌──────────┐                  │ 完成申报后回填
                                                  │ rejected │                  ▼
                                                  │ 已退回   │            ┌──────────┐
                                                  └──────────┘            │  filed   │
                                                                          │ 已申报   │
   任何状态 ──void(需理由+审批人)──▶ ┌──────┐                              └──────────┘
                                    │ void │                                     ▲
                                    │ 作废 │                                     │
                                    └──────┘        calculate → filed  ✗ 不存在这条边
~~~

### 关键设计

1. **`calculated → filed` 这条边在状态机里不存在。** 不是「禁止调用」，是 `TRANSITIONS` 表里根本没有这个目标状态，`canTransition()` 一律返回 false，强行迁移抛 `IllegalTransitionError`。
2. **`filed` 只能由 `reportManualFiling()` 写入**，且必须携带税务局受理回执号 `receiptNo` 与实缴金额 `paidAmount`。它记录的是「人已经做完了」这一外部事实，不是系统动作。
3. **`submitToTaxBureau()` 恒抛 `AutoSubmissionForbidden`。** 这个函数存在的唯一目的是让「想提交」的调用有个明确的失败出口，而不是让调用方去翻文档找接口。
4. **源码级测试**扫描 `src/filing/**`，断言不存在 `fetch(`、`http.request`、`https.request`、`axios`、`XMLHttpRequest`。新增任何外发能力都会让 CI 变红。

### 四眼原则与签名绑定

- `approver ≠ reviewer`：编制、复核、审批三个角色不能是同一个人。
- `allowSelfReview = false` 时 `reviewer ≠ preparer`。
- 每条 `Signature` 都记录签署**当时**的 `payloadHash`。审批时重算哈希，不一致抛 `StaleSignatureError`——防止「签的是 A 版，报的是 B 版」。
- 签署记录只追加，不提供修改入口。

## 三、审计留痕：软删除与历史版本表

### 数据模型

~~~
VersionRecord                                 AuditEvent
├─ versionId                                  ├─ seq          单调递增
├─ entity / entityId                          ├─ actor        谁做的
├─ version        从 1 开始                    ├─ action       create/update/soft_delete/...
├─ data           该版本的完整快照              ├─ before/after 完整前后快照
├─ validFrom / validTo  生效区间               ├─ prevHash     上一条的哈希
├─ deleted / deletedBy / deletedReason        └─ hash         本条哈希
└─ createdBy / createdAt
~~~

### 不变量

1. **只追加**：`*.versions.jsonl` 以 `a` 模式打开，永不重写、永不截断。
2. **更新 = 追加新版本**：旧版本只写 `validTo`，数据字段不动。
3. **删除 = 软删除**：`deleted=true` + 理由 + 操作人；`current()` 返回 null，但 `history()` 永远查得到。
4. **哈希链**：`hash = sha256(prevHash + canonicalJson(payload))`。任何一条被改，`verifyIntegrity()` 会在断链处报出 seq。
5. **时点查询**：`getAt(entity, id, 时间)` 返回那一刻生效的版本——审计要回答的是「上个月 15 号这笔账长什么样」。

### 期间锁账

结账后该期间凭证冻结，任何写入抛 `PeriodLockedError`。反结账必须填理由并留下 `reopen_period` 事件。

## 四、审核引擎：每条结论都有法条

审核不是在界面上弹几个黄条，而是一套可执行的检查项，分五层：

| 层 | 检查内容 | 典型规则 | 依据 |
| --- | --- | --- | --- |
| 凭证层 | 借贷平衡、摘要、附件、日期、兜底科目 | VOUCHER-BALANCE-001 | 会计法第九条、会计基础工作规范第四十八/五十一条 |
| 科目层 | 明细科目、准则白名单、余额方向 | ACC-FORBIDDEN-001 | 小企业会计准则、企业会计准则 |
| 税务层 | 销项与收入勾稽、附加税依据、优惠未享受 | TAX-VAT-MISMATCH-001 | 增值税暂行条例、税收征管法 |
| 刑事层 | 逃税比例、虚开风险、三流不一致 | CRIM-TAX-001 | 刑法 201 条、205 条 |
| 报表层 | 资产=负债+权益、现金流量勾稽 | STMT-BALANCE-001 | 企业会计准则第 30 号 |

### 阻断与豁免

- `error` = 阻断项：未整改不得进入下一环节（结账、导出申报底稿）。
- `warning` = 可豁免，但豁免必须记录「谁、何时、为什么」，且只允许豁免 warning。
- 试图豁免 error 会直接抛错——**监管强制项不允许被人为关闭**。

### 刑事红线的措辞

刑法相关检查在报告里的定位是「风险提示」，不构成法律意见。`detail` 字段固定附带：数额、占比、适用的量刑区间，以及刑法 201 条第四款的出罪路径（首次经税务机关下达追缴通知后补缴，可不予追究刑事责任）。

## 五、双会计准则

`config/settings.yaml` 的 `accountingStandard` 一项决定整套口径：

| 维度 | 企业会计准则 (cas) | 小企业会计准则 (small) |
| --- | --- | --- |
| 递延所得税 | 资产负债表债务法，确认 | 应付税款法，不确认 |
| 资产减值 | 计提减值准备 | 不计提，实际发生才确认 |
| 研发支出 | 费用化 / 资本化分离 | 全部费用化 |
| 收入确认 | 五步法，合同资产/负债 | 开票或收款即确认 |
| 长期股权投资 | 成本法 / 权益法 | 仅成本法 |
| 借款费用 | 符合条件的可资本化 | 一律费用化 |
| 租赁 | 使用权资产 / 租赁负债 | 经营租赁不资本化 |
| 前期差错 | 追溯重述 | 未来适用法 |

切换后会同时切换：科目表、可用科目白名单、报表格式、审核检查集。
例如在小企业准则下，凭证里出现 `1811 递延所得税资产` 会被 `ACC-FORBIDDEN-001` 判为 error 并阻断。

写错（非 `cas` / `small`）会直接抛 `ConfigError`，**绝不静默降级**——用错科目表是比报错严重得多的故障。

## 五之二、准则双轨的完成度（截至本次交付）

必须说清楚哪些做到了、哪些没做到，否则「支持两套准则」就是一句空话。

| 环节 | 企业会计准则 | 小企业会计准则 | 说明 |
| --- | --- | --- | --- |
| 科目表 | ✅ 297 个科目 | ✅ 66 个官方一级科目 | 小企业准则严格照录财会〔2011〕17 号附件 |
| 禁用科目拦截 | ✅ | ✅ | 小企业准则下出现 1811 递延所得税资产会被 ACC-FORBIDDEN-001 判 error |
| 记账规则 | ✅ | ✅ | 只维护一套（企业准则编码），切准则时由 account-map.yaml 自动改写（实测 86 条规则、113 处改写、0 条失效） |
| 折旧/摊销/损益结转 | ✅ | ✅ | 损益结转按科目 category 判断，不靠「6 开头」猜 |
| 合规审核 | ✅ | ✅ | 按准则加载不同检查集 |
| 报表取数 | ✅ | ⚠️ **未完成** | `config/report/statements-small.yaml` 的行次仍是企业准则项目，但科目编码尚未整体改到小企业准则编码（3xxx 权益 / 5xxx 损益） |
| 财务分析 | ✅ 30 项指标 | ⚠️ 受报表取数影响 | 指标本身与准则无关，但输入来自报表 |

**小企业准则下的报表目前会如实报错，而不是悄悄出错**：

- `STMT-BALANCE-001`（资产 ≠ 负债 + 所有者权益）会以 error 出现在审核报告里；
- 利润表营业收入可能显示 0；
- 月结退出码为 2，提示「本期不得结账」。

这是刻意的：宁可让用户看到「这张表不能用」，也不能给出一张数字看起来正常、实际取错科目的报表。
补全工作很明确——把 `statements-small.yaml` 里的科目编码整体替换为小企业准则编码（权益 3xxx、损益 5xxx），
并补一套用真实小企业账簿做的回归测试。

## 六、已知限制（必须如实告知）

1. 系统产出的是**申报底稿**，不是申报结果。税率的适用、优惠的资格最终以主管税务机关认定为准。
2. 政策库中的文件收录截至交付时点，新文件发布后需要更新 `data/policy/`。
3. 刑事红线检查基于金额与比例测算，**不等同于司法机关的认定标准**，仅用于内部风险预警。
4. 系统不保管数字证书、不接入电子税务局，这是设计选择，不是功能缺失。

## 七、如何自证这些约束真的生效

~~~bash
npm test                      # 含源码级断言：无外发请求、无物理删除
node src/cli.ts verify        # 重算哈希链，输出完整性报告
node src/cli.ts check         # 校验配置与准则白名单
~~~

其中两条测试是「结构性」的，不依赖人工纪律：

- `tests/filing.guard.test.ts` —— 扫描 `src/filing/**` 源码，出现 `fetch(` 即失败。
- `tests/audit.verify.test.ts` —— 扫描 `src/audit/**` 源码，出现 `fs.unlink` / `truncate` / `"w"` 写模式即失败。
