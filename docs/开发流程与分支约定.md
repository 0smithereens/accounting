# 开发流程与分支约定

> 本文规定「人 + 子智能体」如何在同一个仓库里并行开发而不互相踩踏。
> 核心原则：**主干永远可发布，任何改动都先落在分支上，验证通过再合并。**

---

## 一、分支模型

| 分支 | 用途 | 谁能直接提交 |
| --- | --- | --- |
| `main` | 随时可发布的版本 | **没人**，只能通过合并进入 |
| `feat/<主题>` | 新功能 | 负责人或子智能体 |
| `fix/<主题>` | 缺陷修复 | 负责人或子智能体 |
| `agent/<名字>-<主题>` | **子智能体专用** | 仅该子智能体 |
| `release/<版本>` | 发布前冻结与打磨 | 负责人 |

命名用小写短横线：`feat/tax-vat-engine`、`fix/small-standard-reports`。

---

## 二、子智能体怎么用分支

子智能体**永远不在 main 上工作**。每个子智能体一个分支，彼此隔离：

```bash
# 1. 起一个专属分支（脚本会自动带上时间戳，避免重名）
powershell -ExecutionPolicy Bypass -File tools/new-agent-branch.ps1 -Name tax -Slug vat-engine

# 2. 子智能体在这个分支上提交（只提交自己负责的文件）
git add src/tax tests/tax.*.test.ts config/tax
git commit -m "feat(tax): 增值税引擎与留抵结转"

# 3. 主智能体合并：先 rebase 到 main 最新，再 --no-ff 合并
git checkout main
git merge --no-ff agent/tax-vat-engine -m "merge: 合并税务引擎分支"
```

### 为什么要 `--no-ff`

合并提交保留了「这一整块工作是一个独立分支」的历史。将来出问题需要回滚时，
`git revert -m 1 <merge>` 可以把整个分支一次性撤掉，而 fast-forward 会把这些提交
摊平成主线上的普通提交，回滚只能一条条找。

### 进一步隔离：git worktree

如果多个子智能体同时改同一个仓库，用 worktree 让它们各有独立工作目录，
连 `node_modules` 与临时文件都不会互相干扰：

```bash
git worktree add ../accounting-tax agent/tax-vat-engine
# 子智能体在 ../accounting-tax 里工作，完成后 git worktree remove
```

## 三、合并前必须通过的检查

```bash
npm run typecheck      # 类型检查必须零错误
npm test               # 全部测试必须通过
npm run check          # 配置校验：科目表、规则引用的科目都存在
```

三条都过才允许合并。CI 上也是这三条，另加一条「用样例跑完整记账并校验借贷平衡」。

## 四、文件所有权（避免并行冲突的根本办法）

并行开发最容易出事的不是代码冲突，而是两个人同时改同一个文件。本项目的约定：

| 路径 | 归属 |
| --- | --- |
| `src/core/contracts.ts` | **主智能体独占**，子智能体只读 |
| `config/settings.yaml`、`config/chart-of-accounts.yaml` | 主智能体独占 |
| `src/cli.ts`、`src/web/server.ts` | 主智能体独占 |
| `src/<模块>/**`、`config/<模块>/**`、`tests/<模块>*.test.ts` | 对应模块的子智能体 |

子智能体发现必须改公共文件时，**写进交付报告由主智能体统一改**，不要自己动手。

## 五、绝对不能提交的东西

`.gitignore` 已经拦住绝大多数，但提交前仍要自查：

| 类别 | 例子 | 为什么 |
| --- | --- | --- |
| 真实账务数据 | `data/audit/`、你自己的银行流水 | 含账号、身份证号、薪资 |
| 赛事材料 | `docs/账有律-项目策划书.md` | 含负责人姓名、团队成员、学校 |
| 会话归档 | `dsh-session-*.zip` | 完整对话记录与本地路径 |
| 凭据 | `.env`、`*.pem`、浏览器 profile | 直接等于交出账号 |

自查命令：

```bash
git status --porcelain
git ls-files | Select-String "策划书|_rules2025|dsh-session|data/audit"
```

## 六、提交信息格式

```
<类型>(<范围>): <一句话说明>

类型：feat / fix / refactor / docs / test / chore
范围：tax / review / report / audit / filing / policy / web / core
```

例：`fix(tax): 附加税计税依据应取实缴增值税而非应纳额`

正文里写清「为什么这么改」，不要写「修改了某某函数」——diff 已经说明了改了什么。
